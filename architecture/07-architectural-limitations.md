# Architectural Limitations

These are the known outstanding issues in the solution architecture as of 5 October 2026, recorded before a stakeholder finds them. Each has an impact, a resolution and a status. Owners are to be assigned by the team (TBD).

Table: Outstanding architectural issues

| Identifier | Issue and impact | Description | Resolution | Owner | Status |
|---|---|---|---|---|---|
| AISS-01 | Cross-schema coupling. Schema changes in `event_inventory` can break other services; services cannot be split onto separate databases yet | The order service writes inventory holds, seats, quantities and queue entries in its own transactions; event cancel writes tickets and orders; the ticket service reads four other schemas. All services share one database user with access to every schema (AD-04) | Short term: one database user per service with grants limited to its schema plus the cross-schema tables it needs, so the coupling is explicit. Long term: move inventory writes behind the inventory API and coordinate reserve, pay and release with an orchestrated saga and compensating release; publish `EventCancelled` instead of writing other schemas | TBD | Open (accepted for this release) |
| AISS-02 | Single database: a single point of failure and the shared scaling limit. A restart means minutes of total downtime; RPO up to 24 hours; no personal-data retention policy | MySQL runs as one Fargate task on EFS with daily crash-consistent backups (AD-13). Every hot path, including queue polling, hits it. Connection pools at maximum scale nearly reach `max_connections` | Measure the limit in the load test. Reduce load (longer poll interval far back in the queue; cache `GET /events` at CloudFront). Roadmap: Aurora Serverless v2 or RDS Multi-AZ with point-in-time recovery; read replica for browse traffic; a retention job for personal data. Assessment tracked in backend #100 | TBD | Open |
| AISS-03 | Notification service is unauthenticated and publicly routed. Anyone on the internet could make the platform send email to any address through the team's Gmail account, or read delivery records (customer emails) by order id | Kong routes `/api/notification` to the notification service, whose `POST /notifications/order-confirmation`, `POST /notifications/event-cancellation` and `GET /notifications/:orderId` check no token. The service is meant to be called only by the ticket service | Remove the public `/api/notification` route from Kong (the SPA does not use it) and require the internal token on all notification routes. Tracked in backend #108 | TBD | Open (found 4 Oct 2026; urgent) |
| AISS-04 | Network and IAM least-privilege gaps. The database is reachable from the internet on port 3306 from personal IPs; task egress is open on 443 and 465; Cognito admin rights are broader than needed | Four MySQL rules on `onestage-ecs-tasks` and one on the default VPC's default group were added by hand (Terraform ignores ingress changes). One task role with Cognito `AdminGetUser`, `ListUsers` and `AdminCreateUser` is shared by five services. One secret holds every credential | Remove the hand-added rules and use ECS Exec or SSM port forwarding for developer access; then fix egress (tfsec). Give the event service its own role without `AdminCreateUser`. Split the secret per purpose | TBD | In progress (rules reduced from about 14 to 5) |
| AISS-05 | No custom domain; HTTP between CloudFront and the ALB. Traffic is unencrypted inside AWS between the edge and the load balancer; email cannot use SES | The distribution uses the default `*.cloudfront.net` certificate and an HTTP-only origin, because there is no domain to issue an ACM certificate for the ALB | Register a domain; issue ACM certificates for CloudFront and the ALB; HTTPS-only origin; add a secret origin header that the ALB requires; move email to SES with the verified domain | TBD | Open (accepted for this release) |
| AISS-06 | Release safety. A bad image reaches every service, with no automatic rollback, no canary and no staging environment | Services run `:latest` with `force-new-deployment`; the ECS deployment circuit breaker is off; one environment (AD-25, AD-28). The proposal promised canary releases | Deploy immutable SHA-tagged task definitions; enable the circuit breaker with rollback; ECS blue/green with bake time and alarm-based rollback for Kong and checkout | TBD | Open |
| AISS-07 | Cognito outside infrastructure as code. The user pool and app client cannot be recreated or reviewed from code; scopes have drifted before (backend #84) | The pool `ap-southeast-1_cgmx4fpO2` and its client were created in the console; their ids are hard-coded in Terraform and the SPA | Import the pool and client into Terraform (`aws_cognito_user_pool`, `aws_cognito_user_pool_client`) and output their ids | TBD | Open |
| AISS-08 | `CustomerAdmitted` events have no consumer. SQS keeps them for 4 days at small cost; buyers still learn of admission only by polling | The queue service publishes one message per admitted buyer, intended for a push channel that was not built | Build a WebSocket or push consumer and lengthen poll intervals, or stop publishing until it exists | TBD | Open (deferred) |
| AISS-09 | Background workers share tasks with the API. A burst of payments competes for CPU with checkout requests; worker capacity follows API CPU, not queue depth | Payment worker, `OrderPaid` consumer, admission scheduler and sweeps run inside the API services (AD-10) | Split workers into their own ECS services scaled on SQS queue depth (backlog per task) when load testing shows contention | TBD | Open (accepted for this release) |
| AISS-10 | Limited observability. Scaling and failures cannot be shown or diagnosed quickly; the DLQ alarm notifies no one | CloudWatch Logs only; no dashboard; Container Insights off; the correlation id from Kong is not passed between services; no tracing; the DLQ alarm has no action | CloudWatch dashboard in Terraform with golden signals, queue depth and task counts; Container Insights during tests; log `X-Request-Id` in every service; SNS topic for operational alarms; OpenTelemetry later | TBD | Open |
| AISS-11 | No published API contract or versioning. Third parties and new clients must read code to integrate; breaking changes cannot be signalled | About 57 endpoints are documented only in "Appendix: API Catalogue"; there is no OpenAPI specification and no `/v1` prefix | Publish an OpenAPI specification for the core endpoints; add a version prefix at Kong; adopt the governance repository's API compatibility rules | TBD | Open |
| AISS-12 | Unused components. An `auth` service runs a task that does nothing; the inventory service's `/holds` endpoints duplicate the order service's reserve path and are not called by the SPA | Both remain from the original design | Remove the `auth` service and its route, or give it a real job; remove or document the unused hold endpoints | TBD | Open |
| AISS-13 | No audit trail of team access. After a member is removed, there is no record that they ever had access to the event | Removing a team member deletes the membership row; the original design's soft revoke was not built | Restore soft revoke (`status`, `revoked_at`) or write membership changes to an audit table. Tracked in backend #109 | TBD | Open |
| AISS-14 | Should-priority acceptance criteria not met | CU-05: no estimated wait time in the queue. OR-08: no attendee export (CSV). (OR-12 is met: only the event owner can remove organisers, nobody can remove themselves, so the owner always remains an organiser) | Compute an estimate from admission rate and position; add CSV export | TBD | Open (deferred) |
